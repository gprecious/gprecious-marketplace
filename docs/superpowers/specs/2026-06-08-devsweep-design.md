# DevSweep — 개발자 디스크 회수 메뉴바 앱 설계

- 작성일: 2026-06-08
- 상태: 설계 승인 완료 → 구현 계획(writing-plans) 대기
- 제품 가칭: **DevSweep** (최종 이름 미정, 문서에서는 가칭 사용)
- 한 줄 정의: 개발 도구가 자동으로 쌓는 캐시·산출물의 **"지금 정리하면 회수 가능한 용량"**을 메뉴바에 실시간 시각화하고, 반자동(감시 + 추천 + 원클릭 승인)으로 안전하게 회수하는 macOS 네이티브 앱.

## 배경 / 문제

개발자 머신은 "따로 설치하지 않아도" 디스크가 계속 찬다. 실측(2026-06-06, 460GB 머신, 사용률 89%)에서 회수한 ~51GB는 전부 **개발 도구가 자동 증식시킨 데이터**였다:

- Docker VM(빌드캐시 + 미사용 이미지) ~27GB
- 패키지 매니저 캐시(pnpm/npm/uv/bun/gradle) ~22GB
- 휴면 프로젝트 node_modules/.venv ~4.5GB
- (별도) 오래된 에이전트 인스턴스 데이터 4.7GB

수동 정리는 (1) 무엇이 회수 가능한지 보이지 않고, (2) **활성 자원을 잘못 지울 위험**이 크다. 실제로 정리 중 `~/.openclaw-pyiri`(4.7GB)는 이름·크기만 보면 중복 사본처럼 보였으나, 프로세스·launchd(KeepAlive)·crontab 세 신호로 참조되는 **운영 중 인스턴스**였다(사용자 확인 후에야 폐기). 이 사건이 본 제품 안전 설계의 핵심 교훈이다.

## 기술 스택 근거 (Swift/SwiftUI 네이티브)

- 상주 앱 + 시스템 깊은 접근(FSEvents, launchd, 프로세스 검사)이 본질 → 네이티브 이점이 결정적.
- 메모리/번들 경량(~30MB / ~10MB대) → "디스크 아끼는 앱이 가볍다"는 정체성과 일치.
- 공증(notarization)·Mac App Store IAP 배포 자연스러움.
- 탈락: Tauri(시스템 API 결국 Rust로 → 2언어 부담, 메뉴바 mac다움 약함), Electron(램 수백 MB·번들 300MB+ = 용량 정리 도구의 자기모순).

## 1. 전체 아키텍처

**단일 앱 프로세스** — 별도 helper daemon 없음. 메뉴바 앱 자체가 상주 프로세스이므로 분리할 이유가 없고 설치·공증·제거가 단순. 로그인 시 자동 시작은 `SMAppService`.

```
┌─────────────────────────────────────────────────┐
│  DevSweep.app (SwiftUI, 메뉴바 상주)              │
│                                                 │
│  ┌───────────┐   주기 스캔    ┌──────────────┐   │
│  │  Watcher  │──────────────▶│ Detector 엔진 │   │
│  │ (타이머+   │               │ (모듈 N개     │   │
│  │  디스크압박)│               │  병렬 실행)   │   │
│  └─────┬─────┘               └──────┬───────┘   │
│        │ 임계치 평가                 │ 스캔 결과   │
│  ┌─────▼─────┐               ┌──────▼───────┐   │
│  │ Notifier  │               │    Store     │   │
│  │ (알림)     │               │ (SQLite:     │   │
│  └─────┬─────┘               │  히스토리/추세)│   │
│        │ 사용자 클릭           └──────────────┘   │
│  ┌─────▼─────────────────────────────────┐      │
│  │  메뉴바 UI (게이지/리뷰/승인/설정)        │      │
│  │  + SkinRenderer (NSStatusItem 그리기)   │      │
│  └─────┬─────────────────────────────────┘      │
│        │ 승인된 항목만                            │
│  ┌─────▼─────┐                                  │
│  │ Safety    │ ◀── 모든 삭제는 이 게이트 단일 통과  │
│  │ Layer     │     (활성 검사·등급·dry-run)       │
│  └─────┬─────┘                                  │
│  ┌─────▼──────────┐  ┌──────────────┐           │
│  │ StoreKitManager │  │  Donation    │           │
│  │ (스킨 IAP)      │  │ (외부 링크)   │           │
```

**핵심 데이터 플로우**: Watcher 주기 스캔(기본 6h + 디스크 압박 즉시) → Detector 병렬 스캔 → Store에 카테고리별 크기 기록(추세) → 임계치 평가 → 알림 → 사용자가 메뉴에서 리뷰 → 승인 항목만 Safety Layer 통과 후 삭제 → 회수량 보고.

**권한 모델**: 홈 영역만 다루므로 sudo 불필요. Full Disk Access 1회 요청(온보딩). 도구의 CLI가 정식 인터페이스인 대상(Docker 등)은 직접 파일 삭제 대신 **해당 CLI 호출**로 내부 상태와 어긋나지 않게.

## 2. Detector 모듈 (정리 대상 엔진)

각 정리 대상을 **독립 모듈**로. 동일 인터페이스 구현 → 신규 대상 추가 = 모듈 1개 추가, 모듈별 독립 테스트 가능.

```swift
protocol CleanupModule {
    var id: String { get }              // "docker", "npm-cache" ...
    var displayName: String { get }
    func scan() async -> [CleanupItem]  // 삭제 안 함. 후보 + 크기만
    func reclaim(_ items: [CleanupItem], dryRun: Bool) async -> ReclaimResult
}

struct CleanupItem {
    let path: String?            // CLI형 대상은 nil
    let sizeBytes: Int64
    let lastUsed: Date?          // 활성 판정용
    let safety: SafetyClass      // .autoSafe / .reviewNeeded / .protected
    let reclaimMethod: ReclaimMethod  // .deletePath(trash:Bool) / .cliCommand(...)
}
```

**모듈 카테고리** (실측 회수 51GB = 모듈 목록):

| 모듈 | 방식 | 안전등급 | 비고 |
|---|---|---|---|
| Docker (빌드캐시/이미지) | CLI (`docker builder/image prune`) | autoSafe | 볼륨 절대 미접근 |
| 패키지 캐시 (pnpm/npm/uv/bun/gradle/cargo/pip) | CLI 우선, 없으면 경로 | autoSafe | |
| node_modules / .venv | 경로 삭제 (휴면 판정) | reviewNeeded | 재설치로 복원 |
| 빌드 산출물 (target/, dist/, build/, DerivedData) | 경로 삭제 | reviewNeeded | |
| Xcode (DerivedData/iOS DeviceSupport/시뮬레이터) | CLI+경로 | reviewNeeded | |
| AI 에이전트 데이터 (캐시성만) | 경로, **활성 검사 강제** | reviewNeeded | pyiri 교훈 |
| 범용 (브라우저 캐시/휴지통/대용량 탐색) | 경로 | reviewNeeded | |

**설계 원칙**:

1. **CLI 우선 (state-aware reclaim)** — 도구가 자체 캐시 관리 CLI를 제공하면 파일 직접 삭제 대신 그 CLI를 호출(내부 인덱스와 정합 유지).
2. **scan / reclaim 완전 분리** — scan은 절대 삭제하지 않음. 후보·크기·안전등급만 계산. 삭제는 승인 후 reclaim에서만, 항상 Safety Layer 경유.
3. **모듈 자동 감지** — 미설치 도구는 `scan() → []` + UI 숨김. 머신별 스택에 자동 적응.

## 3. Safety Layer (제품의 심장)

**모든 삭제는 예외 없이 이 레이어를 단일 통과한다.** scan에서 후보가 올라와도 이 게이트를 못 넘으면 절대 삭제되지 않는다.

### 4단계 게이트 (순서대로, 하나라도 막으면 reclaim 중단)

**① 안전등급 분류 (SafetyClass)**

```
.autoSafe      → 도구가 재생성 보장하는 순수 캐시 (npm/pnpm/uv/docker 빌드캐시).
                 반자동에서 사용자가 "이 카테고리 자동 허용" 켰을 때만 무승인 삭제.
.reviewNeeded  → 재설치 비용 있음 (node_modules, 빌드산출물). 항상 명시적 승인.
.protected     → 절대 건드리지 않음. UI에 후보로도 안 띄움.
```

**② 활성 검사 (pyiri 방어 — 핵심)**

삭제 후보 경로마다 "지금 쓰이고 있나"를 다중 신호로 검사. **하나라도 걸리면 `.protected`로 강등**:

- 프로세스 참조 — `lsof`로 해당 경로를 연 프로세스
- launchd 등록 — `~/Library/LaunchAgents` + `launchctl list`의 경로 참조
- crontab 참조 — `crontab -l`의 경로 등장
- 최근 사용 — mtime/atime이 임계일(기본 30일) 이내
- 부모 프로젝트 활성도 — node_modules 부모에 30일 내 수정 소스 존재

> pyiri 검증: ①에서 4.7GB 후보로 보여도, ②의 프로세스(포트 18790)·launchd(KeepAlive)·crontab 세 신호에 동시 적중 → 자동 `.protected` 강등 → 후보에서 제거. 사람이 명시적으로 "사용 안 함"을 확인해야만 폐기. **이 동작을 회귀 테스트로 박제한다.**

**③ 보호 목록 (Protected Registry)**

- 사용자 영구 제외 경로 + 시스템 기본 보호(`~/.ssh`, `~/Library/Keychains`, `.git` 등)
- 한 번 "보존" 결정한 항목은 기억 → 다음 스캔에서 다시 묻지 않음 (반복 평가 방지)

**④ Dry-run + 회수 검증 + 되돌리기 여지**

- 삭제 전 영향 목록·예상 회수량 표시(dry-run)
- 경로 삭제는 가능하면 **휴지통 이동(`FileManager.trashItem`)**. 큰 캐시는 휴지통 무의미 → 카테고리별 휴지통/영구 정책 분리
- 삭제 후 실제 회수량 측정 → 예상과 대조 보고

**감사 로그**: 모든 삭제를 Store(SQLite)에 기록 — 무엇을/언제/얼마나/방식. "뭐가 지워졌지?"에 항상 응답.

## 4. Watcher · Notifier (감시·알림)

### Watcher — 언제 스캔하나

세 트리거:

1. **주기 스캔** — 기본 6h(설정 가능). `NSBackgroundActivityScheduler`로 시스템이 전력/유휴 보고 효율적으로 깨움.
2. **디스크 압박 즉시 스캔** — 여유 용량이 임계치(기본 15%) 아래로 떨어지면 즉시.
3. **수동 트리거** — 메뉴의 "지금 스캔".

> FSEvents로 캐시 디렉토리 실시간 감시는 **안 함** — 캐시/node_modules는 변경이 폭발적이라 우리 앱이 자원을 잡아먹는 자기모순. 주기+압박으로 충분.

**스캔 비용 관리**: 모듈 병렬 실행. `du` 같은 무거운 계산은 캐싱+증분 — 디렉토리 mtime 불변 시 이전 크기 재사용(매번 전체 디스크 미순회).

### Notifier — 어떻게 알리나

`UNUserNotificationCenter` 기반. **알림 피로 방지가 설계 핵심**:

- **회수 가능량 임계 초과 시에만** (> 20GB 기본)
- **스로틀링** — 같은 임계 구간에서 하루 1회 초과 금지. 무시하면 다음 단계로 커지기 전엔 재알림 없음
- **알림에서 바로 행동** — `UNNotificationAction`: "리뷰하기" / "안전 캐시만 정리"(autoSafe 원클릭) / "오늘 그만"
- **조용한 기본** — 평소엔 메뉴바 게이지로만. 시스템 알림은 진짜 임계 이벤트에만

**자동 처리 경계** (반자동): `.autoSafe` 중 **사용자가 명시적으로 "자동 허용" 토글한 카테고리만** 무알림 자동 정리. 그 외 전부 알림 → 승인.

## 5. 메뉴바 인디케이터 (회수 가능 용량 시각화)

RunCat이 쓰는 `NSStatusItem.button.image` 타이머 갱신 메커니즘 동일. RunCat이 "CPU 부하 → 고양이 속도"였다면, DevSweep은 **"쌓인 회수 가능량 → 시각 신호 강도"**.

**핵심 지표**: `reclaimableBytes` = 마지막 스캔의 모든 `CleanupItem.sizeBytes` 합.

**기본 표현**: 충전식 게이지(회수량 쌓일수록 채워짐) + 20GB 초과 시 애니메이션/숫자 노출.

**임계 구간** (절대 여유 용량이 아니라 회수 가능량 기준):

- `< 5GB` → 게이지 거의 빔, 정적, 회색 (정리 불필요)
- `5–20GB` → 노랑, 약한 표시
- `> 20GB` → 빨강 + 애니메이션 + 숫자 노출 + (반자동) 알림 트리거

**설정**: 표시 방식 선택(아이콘만 / 아이콘+숫자 / 끄기). 평소 정적, 변화 시에만 애니메이션 → "디스크 아끼는 앱이 자원을 아낀다" 정체성 유지.

**보조 지표**: 디스크 여유 용량은 드롭다운 메뉴 안에서만 보조 표시. 메뉴바 본체는 회수 가능량 전용.

### 메뉴바 디자인 제약 (리서치 반영)

- 작업 영역 22pt(그림은 16×16pt 기준). 노치 머신 세로 여백 가변 → 여백 가정 금지.
- **템플릿 이미지(알파 채널만)** → 라이트/다크/Reduce Transparency 자동 대응. 모노크롬 = 운영비 0.
- 색 대신 **불투명도**로 단계 표현. 회수량 = "채움 높이 + 부분 opacity".
- 상시 회전보다 **상태 전이(idle→채움→비움/터짐) 키 모먼트**가 22pt에서 잘 읽힘(트랜지션 200~500ms).
- 유휴 시 0fps, 회수량 비례 6~15fps만 → 발열·배터리 최적. `transform/opacity`만 애니메이션.
- 스킨 키프레임 규격(RunCat 사실상 표준): PNG, 높이 36px, 너비 10–100px, 최대 50프레임.

## 6. 수익화 (RunCat 정통 모델)

**모든 정리 기능은 영구 무료. 페이월 0.** 수익은 두 갈래.

근거: Stats(무료 오픈소스, 39k stars)가 증명하듯 **기능 경쟁으로는 못 이긴다.** 차별화·수익은 100% "보고 싶은 스킨"에서. DevSweep만의 강점: 스킨이 디스크 상태에 **반응**(정보 표현 방식 자체를 판매 — 정적 러너보다 구매 명분 강함).

### (A) 스킨 IAP — Mac App Store StoreKit 전용

| 항목 | 가격 | 성격 |

## 7. 테스트 전략

**남의 파일을 지우는 앱** → "안전성 회귀 방지"가 1순위. pyiri를 살린 판정이 영원히 깨지지 않아야 한다. **위험도 순서 = 테스트 두께 순서.** TDD로 Safety Layer부터(test-driven-development 스킬 적용).

### ① Safety Layer — 최우선, 가장 두껍게 (XCTest)

- **활성 검사 회귀 픽스처**: 가짜 프로젝트 트리 + 모의 프로세스/launchd/crontab 신호로 "pyiri 시나리오" 재현 → `.protected` 강등 검증. **깨지면 빌드 실패**(안전 계약)
- 안전등급 분류, 보호 목록(영구 제외 기억), 휴면 판정(mtime 임계일 경계값) 각각 단위 테스트
- **파괴적 작업 전부 추상화 뒤로** — `FileSystemDeleter` 프로토콜로 실제 삭제 격리. 테스트는 mock, 실제 `rm`/`trashItem` 호출 0
- **dry-run 불변식**: scan은 절대 삭제 안 함 검증 (mock deleter 호출 카운트 0)

### ② Detector 모듈 — 모듈별 독립

- 각 모듈을 픽스처 디렉토리(임시 tmp)에 scan → 예상 후보·크기 일치
- 도구 미설치 시 `scan() → []` + UI 숨김
- CLI형 모듈(docker/pnpm)은 CLI 호출 모킹 — 실제 도구 의존 없이 명령 구성·파싱 검증

### ③ 회수량 매핑·렌더링 — 결정적

- `reclaimableBytes → 시각변수(Fill/Speed/Glow)` 매핑: 경계값(5/20GB) 스냅샷 테스트
- 스킨 렌더러: 회수량별 `NSImage`를 골든 이미지와 픽셀 비교(다크/라이트/투명도끄기 3모드)

### ④ StoreKit — StoreKit Testing 프레임워크

- 로컬 `.storekit` 설정으로 구매·복원·환불 플로우 자동 테스트(실결제 없이)
- 라이브 프리뷰 → 미결제 시 원복 검증

### ⑤ 통합/수동 게이트 (CLAUDE.md HARD GATE 준수)

- 실제 메뉴바에 앱 띄워 게이지 애니메이션·알림·승인 플로우 눈으로 확인(자동화 불가 영역)
- **실삭제 통합 테스트는 격리된 임시 디렉토리에서만** — 절대 실 홈에서 안 함
